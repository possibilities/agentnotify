# Native notification inbox design

The person opens this panel to decide what still needs attention and take the next action. Content, read state, and completion lead; product identity and transport status do not occupy a rail.

## Visual language

A continuous semantic window surface, SF system typography, and grayscale controls. System appearance selects light and dark automatically. A functional category menu, count, search, filters, and a detach control occupy the top. The category’s custom chevron has an explicit 8-point gap; the count stays outside the menu label so AppKit does not compress the composition. Notification rows share a title/body/metadata/action alignment without enclosing cards. The selected row gets a subtle surface; every other boundary must earn its space.

Type roles: 20-point semibold category, 13-point semibold titles, 13-point regular body, 11-point metadata. Outer inset 20 points, row inset 10, restrained 6-point control radii, 28-point icon targets. Default popover 440 × 610; the detached panel supports 360–700-point widths. Use semantic colors, never fixed light/dark overrides in production. Relative dates omit ticking seconds.

## Behavior

Inbox, Unread, Later, Done, and All are status views. Search matches title, subtitle, message, and group. Group filtering is exact; time filters use creation time. Long content expands in place. Reading does not complete or execute a callback. A native checkbox marks completion. The confirmation names the completed notification and offers “Undo completion”; its close control only hides the confirmation. A native context/menu surface carries less frequent operations.

One action is a button; multiple actions form an Options menu; a reply expands an inline field. Explicit body callbacks have a distinct Open, Open App, or Run Action control. Their target is inspectable in details. A notification without a supplied action gets no fabricated primary action.

The popover and detached panel reuse one hosting controller and model. Hiding a window never changes task state. API/MCP `show` can select a notification and choose detached presentation.

Pinning preserves the content's screen coordinates and the toolbar's control positions. The pinned panel stays visible over other apps, without the popover pointer. Both presentations stay where placed; neither follows menu-bar auto-hide. The panel uses a transparent borderless window with a continuous 20-point corner to match the popover body. Drag blank space anywhere on the panel to place it independently, including the header, margins, empty body, and space around or below notifications. The outer resize edge retains native resizing. Once moved, unpinning keeps that window, position, and triangle-free outline; it only enables hover dismissal. Closing an unpinned window and opening it again restores the anchored popover. An untouched panel still returns to the tray when unpinned. Close lives in More in both presentations. The native popover uses an invisible anchor kept within its display because macOS can move an auto-hidden status window off-screen. See [the positioning decision](adr/0002-stable-menu-bar-anchor.md).

Opening a panel does not automatically focus the category menu. Pointer input clears control focus while preserving an active text editor. Tab and keyboard menu navigation retain native focus indication; VoiceOver retains native focus behavior. Do not suppress every focus ring to make a surface quieter.

Dragging keeps one screen-space grab point for the whole gesture. Use the mouse event's global position and the captured starting window origin; converting queued window-local positions through an already moved window creates feedback and jitter. Explicit background drag surfaces own dragging, with native background dragging disabled. They sit behind interactive content, with a second surface inside the scroll view filling at least its viewport; controls, text input, and scrolling retain their normal behavior. Mouse-up or changing windows clears the gesture. This preserves the grab point through direction changes without tethering the panel to the menu bar.

An unpinned inbox stays open under the pointer, whether it is an anchored popover or a manually placed panel. After the pointer leaves the popover and tray icon, it dismisses after one second; returning cancels the countdown. Opening from the CLI or API does not start a countdown until the pointer has visited. Native menus pause dismissal, while text editing, keyboard navigation, and VoiceOver keep it open. A pinned panel never dismisses on pointer exit. Window tracking and local/global mouse events drive a one-shot delay, with no position tracking. Movement outside recovers a missed frame-exit event and returns control from keyboard navigation. Once the pointer leaves, continued outside movement does not restart the deadline. Returning cancels it; ending a sheet or text editing can resume it. Closing or pinning removes the event monitors and restores the window’s prior mouse-movement policy.

## Arrival previews

The compact arrival and durable inbox answer different questions: what just arrived, and what still needs attention. The default Queue Peek design is a 440 × 126-point peek into the inbox, with its semantic surface, SF type roles, and continuous 20-point outline. A subtitle (or group) identifies context, followed by the title and up to two message lines. The quiet footer says “New · 3 waiting” or “3 new · 8 waiting.” Waiting includes read, unfinished tasks. The tray keeps that count after the preview disappears, capped visually at 99+ with the exact count in its accessible label and tooltip.

One nonactivating panel appears beneath the safe menu anchor. It stays still while shown, and opening the inbox uses the captured anchor so an updated tray count cannot shift the handoff. It fades in for 160 ms; Reduce Motion removes the fade. After five seconds it dismisses without a store mutation. Hover pauses the timer, leaving gives at least 1.5 seconds, and VoiceOver holds the preview with a polite announcement. The whole body opens the displayed notification; the small X only dismisses the preview. Opening reads the item but never answers, completes, or runs an action. Finish the original mouse-up before creating the transient popover.

Bursts update the same renderer/window. Content and clicked identity stay frozen under hover or a press; the footer updates and the latest item appears after leaving. Group replacements stay durable. If a hovered lead was replaced, a click can still inspect that exact historical item; the full inbox owns current response availability. New arrivals while the inbox is open add a small cue inside it without moving the window, changing the current selection, or putting a second panel over it. Reading or using the cue clears it.

The durable `created` and `due` change events drive arrivals, with a launch cursor baseline. Read, delivery, reopen, and callback bookkeeping never replay arrivals. Eligibility is checked again against current state before presentation. A single visual delivery owner prevents duplicate banners: the compact preview is used for denied/not-determined authorization or disabled native alerts; enabled native banners retain system sound, action, and Focus behavior. There is no attempt to infer whether Focus hid an individual system banner. Custom previews do not change native delivery receipts or the legacy CLI contract, and never add an unrequested sound.

Debug `arrival-studio` opens a separate native controller and synthetic target. It compares this design with a smaller conventional banner and a queue-footer alternative, with single/burst/long scenarios and light/dark appearance. Studio selections are transient and do not change saved preferences. `render-arrivals <directory>` produces 18 actual SwiftUI renders. The studio and bounded `AGENTNOTIFY_ARRIVAL_PREVIEW_HOLD=1` gesture-inspection hold (requires an isolated state directory) are excluded from release builds.

The controller and target start beside each other; moving the controller or choosing Arrange windows reunites them. Design and scenario changes reveal the compact preview, while appearance changes update whichever surface is open. Show preview holds it for inspection; Play arrival fades in and runs a five-second dismissal with hover/VoiceOver holding. The controller reports the current presentation and disables redundant actions. Opening the inbox cancels playback, and sample completion/Undo updates the waiting count. Pinning controls the synthetic inbox's hover dismissal without moving it. Settings explains the synthetic boundary instead of opening system preferences. AppKit owns explicit hosting sizes so content updates cannot collapse or displace the borderless target.

To restore a person's transient choices after a debug rebuild, pass all three selections: `arrival-studio compact-toast burst light`. The optional tuple is design (`queue-peek`, `compact-toast`, `queue-shelf`), scenario (`single`, `burst`, `long`), and appearance (`light`, `dark`). This restores the comparison only; it does not adopt a production design or save a profile. Studio playback exercises the comparison surface, not system delivery or the production burst tracker.

## Preferences and system settings

More → Preferences opens a native, theme-following window. Appearance contains a segmented Arrival style picker: Queue Peek (default, 440 × 126), Compact Toast (360 × 96), and Queue Shelf (440 × 144). All three ship in production and use the same renderers as the labeled, noninteractive preview and debug studio. Preference changes apply to the next arrival; a visible target keeps its design and dimensions through the current interaction. One AppKit sizing owner keeps the window stable while content changes.

Preferences are stored separately from notification state, with a revision and conditional writes shared by CLI, socket, MCP, and GUI. Changing appearance neither completes a task nor adds a notification change event. A Terminal integration section offers Install shim (or Reinstall shim when already installed), its location, and the preserved original-notifier fallback. The Appearance composition stays unchanged above it.

When native banners are unavailable, the inbox offers one quiet “Turn on macOS banners” action. It requests initial permission or opens notification settings. Recheck authorization, alert availability, and alert style when apps activate, the Mac wakes, the inbox opens, or Preferences opens. While either window is visible or System Settings is foreground, refresh every three seconds; otherwise stop polling. Discard stale asynchronous settings reads. A person changing banner settings should not need to restart the app, and enabling native banners dismisses any compact preview to retain one arrival owner.

The first inbox or Preferences opening offers terminal-notifier integration once, with Install shim and Not now. Background delivery never triggers the offer. Record its presentation durably before showing it; skipping, quitting, or a failed install must not create a recurring dialog. Already-installed fleet routers need no offer. The same button remains available in Preferences, with progress and visible installation errors. AgentStart owns the single shim installer, while AgentNotify owns this opt-in experience. Show the install location and PATH ordering because those determine which executable existing scripts reach; do not edit shell profiles or replace an unrelated command.
